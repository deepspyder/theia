# vivo X200 Ultra 导出管线兼容性排查

日期：2026-11-16。基线提交：`32855c3`，原安装包为 Theia v0.1.7，versionCode 8。

## 客户现象与判断边界

客户设备为 vivo X200 Ultra，反馈 Android 17、系统 `PD2454C_A_17.2.12.0.W10.V00 OL1`、相机 13.0.55.13。两张客户 JPEG 分别为 3072×4096 与 4096×3072；错误截图选择 2560 px、JPEG，显示 `SpkException: Vulkan compute pipeline failed (VkResult -13)`。客户操作包含切换胶片、相纸、调整曝光、亮度、对比度和开启日期后背，其他格式也失败。实际胶片、相纸、日期样式与具体调色值未知。

`-13` 是 `VK_ERROR_UNKNOWN`。旧代码把描述符布局、管线布局和计算管线创建失败都压成同一条文字，截图不能区分具体 Vulkan 调用，更不能定位失败内核。不能据此认定照片损坏、日期后背错误、显存不足，或 Android 17 全面不兼容。

模拟器使用 API 37、x86_64、Goldfish GFXStream，宿主 GPU 为 NVIDIA GeForce RTX 5060。原版 Release 原生库在两张客户照片和全尺寸 NEF 上通过 17 组完整调度与窗口调度比较，没有复现客户的自然失败。因此，厂商驱动兼容性是待真机确认的方向，不是已经证明的根因。

## 修改范围

- Android 适配层把创建阶段、准确的内核名（含 `.windowed`）、GPU、厂商、设备及驱动版本写入失败信息。区分 `vkCreateShaderModule`、`vkCreateDescriptorSetLayout`、`vkCreatePipelineLayout` 和 `vkCreateComputePipelines`。
- 仅当计算管线创建返回 `VK_ERROR_UNKNOWN` 时，清理可能残留的管线句柄，使用 `VK_PIPELINE_CREATE_DISABLE_OPTIMIZATION_BIT` 重试一次。模块、入口、布局、特化常量和工作组全部保留，成功后进入原有管线缓存。
- 成功的正常路径只调用一次创建。设备丢失、主机内存不足、设备内存不足不进入该重试；重试仍失败时报告两次结果，不无限重试。
- 添加仅通过 ADB 设置的 `debug.theia.pipeline_retry_test=1` 故障注入。它让窗口着色器的第一次创建模拟返回 `-13`，第二次真正调用同一 Release 原生创建逻辑，用于测试兼容路径。正常使用不设置此属性，验证后恢复为 0。
- 着色器编译工具增加 `--spirv-val`，在编译时验证全部普通、有界及窗口化 SPIR-V。失败输出同时保留标准输出和错误输出。

共享 Windows 引擎、胶片与相纸光谱数据、着色器算法和二进制、照片解码、尺寸、位深、编码质量和数据库均未修改。未降低分辨率或关闭效果绕过失败。

这项重试是有边界的兼容措施，不能保证厂商驱动一定接受关闭优化标志。驱动也可能忽略该提示；触发重试后首次编译或后续执行速度可能变化，需要真机测量。正常路径不主动关闭优化。

## 验证合同与证据

本地证据目录为 `.tmp/vivo-export/`，客户原片、测试输出与安装包不提交仓库。

- 两张 JPEG 原始字节分别为 5,482,417 与 6,669,903；SHA-256 分别为 `34cd47831bbe2b3e514dbf7476a06263705a612aad029817db8d7f254792eb5e`、`9c3b94e0bca188991ffc81bb0763f87c3ff15fbc90c79d55b6d62446dc97536b`。
- 全部 143 个着色器通过 SPIR-V 验证，并与原 v0.1.7 打包的 143 个二进制逐字节相同。
- 原生重试状态机覆盖 30 组结果组合，验证最多两次创建、失败半成品释放、其他创建标志保留、错误分类和失败上下文。
- 17 组 RGBA16 全通道摘要：两张客户 JPEG，各覆盖 Portra 400、CineStill 800T、Velvia 100、HP5 Plus，日期后背开关；另含 CineStill 800T 配 Vision 2383、背反射光晕和真实 NEF 原尺寸 6064×4040。曝光、亮度、对比度均设置非零，颗粒、光晕保留。原版、修改版完整调度、强制重试窗口调度全部摘要相同。
- 实际应用测试宿主使用同源码 Debug UI 与 Release 原生库，通过正式独立渲染进程、缓存与相册保存路径导出。宿主 DEX 不冒充与 Release 相同；最终 Release 的 DEX 与基线另行字节核对。

测试构建中曾把 Vision 2383 夹具内部 ID 写成不存在的 `kodak_vision_2383`，首次测试因此明确失败。已更正为真实 `kodak_2383` 后重新完成基线及重试验证；该失败不是客户报错的复现。

## 实际文件矩阵

两张客户原图分别导出 33 张，总计 66 张：Portra 400 分别关闭、开启日期后背，各覆盖 2048、2560、3840、原尺寸；CineStill 800T、Velvia 100、HP5 Plus 开启日期后背，各覆盖 2560。每组均输出 JPEG、PNG、TIFF sRGB。其他胶片未声称完成全部尺寸排列；P3 没有作为本轮新矩阵项目。

全部通过应用的独立 `:render` 进程和正式相册保存链路，刻意注入首次管线创建失败，确认重试被实际执行，日期遮罩内核 `spk_overscan_add_mask.windowed` 也确实经过重试。PNG/TIFF 可复用已验证的同一成片缓存；每个尺寸、材料和日期组合先清除衍生成片缓存。

随后由独立 Python 解码器核对整个文件，而不是只读头部或缩略图：22 张 PNG 的 RGB8、22 张 TIFF 的 RGB16 全通道差异为 0；22 张 JPEG 与无损参考的最大单图平均绝对通道差为 2.732819/255。JPEG 本身有损，不能要求和无损参考像素相同。全部输出尺寸与独立同尺寸完整渲染一致，原尺寸严格保留 3072×4096 或 4096×3072。日期开关在八个照片/胶片组合上都改变像素，排除测试中效果未启用的假通过。

证据：`matrix/pixel-verification.json`、`matrix/native.log`、`native-verification.json`、`verification.json`。

## RAW 性能对照与限制

关闭所有测试开关后，原版与修改版按 before/after/after/before/before/after 交错各三轮，包含无颗粒/眩光的原生原尺寸 TIFF，以及保留 CineStill 效果的正式应用冷导出与缓存导出。六轮各自的成片文件摘要完全一致，GPU 池帧峰值均为 1,243,027,572 字节，没有新增整图缓冲。

| 测量项，中位数 | 原版 | 修改版 |
| --- | ---: | ---: |
| 原生 RAW 完整解码、校正、渲染与 TIFF 编码 | 5677.54 ms | 5811.25 ms |
| 其中原生渲染阶段 | 1985.86 ms | 2097.50 ms |
| 应用 CineStill 原尺寸冷导出 | 8596 ms | 8558 ms |
| 应用 CineStill 原尺寸缓存导出 | 853 ms | 839 ms |

应用端冷导出为 -0.44%，缓存导出为 -1.64%；原生单项总耗时 +2.36%、渲染阶段 +5.62%。三轮样本不能把单项变化全部归为噪声，也不能据此保证所有设备没有性能代价。解码与校正未修改但同样出现约 4% 变化，说明存在运行环境波动。正式应用端在本轮未观察到整体导出变慢；ARM 厂商驱动与真实关闭优化后的耗时仍需真机测量。

原生性能测试使用设备中的 `perf-z6ii.NEF`，当前实际字节是 Nikon Z 6_2 无损样本 `1b67d15817dbd4143a1f1089e2f09e319a2a2327c124e2643284509dd7621030`；17 组画质测试另使用 `pc-parity-DSC_5099.NEF`，SHA-256 `cafd8050d216fd08923eb972221c2011c2a4d39cda33efb6b0ed39e2a77ede3b`。性能脚本初次沿用历史 DSC_5099 摘要，因此明确失败；确认设备文件内容与历史别名不同后，改为当前原版建立同场摘要，严格验证修改版及所有后续原版轮次相同，没有放宽像素阈值。

证据：`raw-benchmark/runs.json`、`raw-benchmark/summary.json`。

## 2026-11-17 真机复测：兼容重试仍失败

客户安装上述验证包后的新截图明确报告：

```text
vkCreateComputePipelines failed
VkResult=-13
kernel=spk_couplers_correction.windowed
gpu=Adreno (TM) 830
vendor=20803
device=1141178369
driver=2150760528
compiler_retry=-13->-13
```

这份真机证据否定“关闭编译优化重试已经解决该客户问题”的结论。旧的模拟器画质与格式验证仍然成立，但只证明模拟器上的正确性和故障注入路径，不能作为这条 Adreno 驱动管线的兼容验收。截图选择 JPEG 原始尺寸，上一张截图在 2560 px 也失败，因此不能把本次错误简单归因于原尺寸过大。

当前可以确认的失败边界是 `vkCreateComputePipelines`；着色器模块和管线布局创建已成功，尚未向这条计算管线提交像素计算，也未进入文件编码。具体内核负责 `Pipeline::node_dir_couplers` 中、空间扩散之前的染料耦合校正，输入为 CMY、3×3 校正矩阵、最大密度、正片标志、位移与像素数量。它不是日期后背遮罩内核，JPEG/PNG/TIFF 共用此处的胶片处理，因此换格式不能规避同一失败。

源码对照确认窗口化变体保留原有浮点公式，新增全局基址、末端保护和逐绑定相对地址。当前生成器连始终整块绑定的小型矩阵、标志及计数表也使用 `uint(index) - origin[binding]`，扩大了编译器需处理的动态寻址范围。这是值得收敛和做差分验证的兼容候选点，不是已经被真机证明的触发原因；SPIR-V 验证通过也不足以确定厂商驱动能够编译。

后续应对该内核做有针对性的差分：保留图像输入/输出窗口偏移，简化固定参数寻址，或为这条无空间依赖、无随机数的点运算实现经对齐与尾部证明的原始内核分批调度。二者都需要完整 RGBA16 对照、正负片与 DIR 参数边界验证，再在客户驱动上确认。不能直接关闭 DIR 校正或退回超出设备绑定范围的整图调度来宣称修复。

状态：失败阶段和内核已定位；实际 Adreno 830 失败未修复。当前没有证据把问题归因于 JPEG 原片损坏、日期文字、格式编码或整个 Android 17 系统不支持。

后续实现记录：2026-11-17 已实现原始 DIR 内核的对齐分批调度，主动避开此窗口化模块。新的像素、格式和性能证据及独立验证包见 `adreno830-local-dir-2026-11-17.md`；客户同一驱动上的复测仍待完成。
