# RAW 原始尺寸片边导出排查与回归

## 输入与结论边界

本轮开始于 2026-11-17，测试跨至本地次日完成；证据目录保留开始日期。

用户提供 `DSC_5099.NEF`（SHA-256 `cafd8050d216fd08923eb972221c2011c2a4d39cda33efb6b0ed39e2a77ede3b`）及两张异常 JPEG，尺寸分别为 6301×5819、6314×4395。反馈设备为小米 17 Pro，使用自行打包的 app-release，未旋转照片；较小尺寸正常，vivo 兼容适配前未遇到此问题。

本轮按用户选择只使用模拟器，API 37 / Android 17、x86_64、GFXStream。没有连接小米或 vivo，不能将以下结果描述成已复现或已修复 Qualcomm 专有驱动上的错位。默认策略下，修复前的同 NEF 全尺寸 CineStill 输出在模拟器上已经可以与整图参考逐像素一致。

已确认、修复三个可独立验证的问题：

1. **片边跨网格节点仍有整图绑定。** `spk_overscan_canvas` 和 `spk_overscan_add_mask` 原属 `Opaque`，虽然分批提交，仍把完整输入/输出绑定给每一批。全尺寸片边 RGB32 平面可超过 400 MiB。将后端硬绑定限制为 128 MiB 后，旧构建在 `spk_overscan_canvas` 明确失败；修复后同 NEF 在 128 MiB 硬上限和 8 MiB 工作窗口下完成 6301×5819 正式 PNG 导出。这是已证明的执行合同缺口，并不等于已经证明它是小米截图的唯一原因。该缺口在 vivo 适配之前已有，不能仅根据反馈时间把它称为 vivo 新引入的错误。
2. **亮齿孔掩盖了黑带检测。** 旧判断要求连续缺失行和全图相关性低于 0.25 同时成立。P1 与本轮正常片边参考的相关性约 0.32694，48×32 采样中的 14 行连续缺失，旧门槛会漏检。新增相同类型用例在旧宿主上实际失败，新判断不再让完整齿孔抵消连续缺失行的证据。P2 的离线参考采用本轮设置，不能冒称完全还原其未知编辑参数。
3. **观景台取消导出未通知输出面板。** 完整 UI 回归在最后的取消步骤超时；现场已经结束进度，但没有成功或取消状态。`ExportCancelled` 继承协程取消异常，旧通用分支直接抛出，导致 `outcome` 为空，`onFinished` 没有调用。现仅对用户取消设置失败结果，经原有 finally 回传面板；真正的生命周期协程取消仍传播。渲染、编码和提交算法不变。

## 实现

- `window_plan.hpp` 为胶片画布、文字遮罩设置独立类型及移动绑定合同；参数和计数表仍保持固定索引。
- `WindowedDispatch.cpp.in` 根据胶片扫描仿射变换、竖向画幅、门边反光和双曝光参数规划保守源行区间，保留双线性邻域与浮点舍入余量；目标画布和遮罩分别限定到本批实际读写的行。
- 所有区间仍受设备偏移对齐、工作窗口和硬绑定范围约束。原图坐标、颗粒随机编号、物理片边、文字覆盖和浮点照片运算保持；不缩小原始尺寸，不关闭颗粒/光晕，不用预览代替成片。
- 更新 renderer 身份为 `scalar-origins-v3-film-windows-1`，避免旧成片缓存掩盖执行变化。
- `RenderAppearance` 对有明确亮度参考的连续四分之一画面黑带独立拒绝；保留平坦参考、噪声容忍和结构丢失的原检查。

与任务开始保存的 Release 比较，193 个共同引擎资源中只有上述两个 `.windowed-v3.spv` 改变，其余 191 项相同。原始着色器、其他窗口内核、材料光谱数据、RAW 解码和输出位深不改。

## 验证方法

测试使用同源码 Debug 界面装入本次 Release 的六个原生库；引擎资源也与交付 Release 完全相同。不能称测试宿主 DEX 与正式 Release DEX 相同。

- `OverscanExportAudit`：真实原始尺寸 NEF，CineStill 800T / Vision 2383，颗粒、眩光、背反射和日期开启。135、半格、宽幅的完整 RGBA16 摘要与独立整图调度一致，并与任务开始的模拟器结果一致。
- `ExportMatrixAudit`：真实编辑器 → 独立 `:render` 进程 → 文件编码 → MediaStore。输出在电脑独立解码，每个 RGB8 / RGB16 通道都比较，不只看缩略图、文件头或成功提示。JPEG 与相同质量、相同系统编码器处理独立整图渲染结果的参考比较；不把 JPEG 与无损 PNG 的正常压缩差异当成渲染故障。
- NEF 矩阵覆盖无片边、135 整条、135 扩展片门、半格；每种均覆盖 2048 / 2560 / 3840 / 原始，以及 JPEG95、PNG、sRGB TIFF16、Display P3 TIFF16，共 64 张。均通过完整解码比较，最大通道差异 0。
- JPEG / PNG / WebP 真实照片与 50MP DNG 各覆盖四尺寸、四格式，另 64 个去重文件通过；合计 128 张完整解码最大通道差 0。50MP DNG 的带片边原尺寸输出为 7910×8564。其初轮最后一张 P3 TIFF 因模拟器 10GB 数据分区不足返回 ENOSPC；调整测试采集为每张即时转存/验证/回收，仅重跑受影响 DNG，16 张最终全部通过，不能把首轮空间失败隐去。
- 全应用回归和重复耗时以最终附加的测试结果节为准。
- `BoundedExportAudit` 扩充十种片边画幅、两种模式、不同种子和旋转，针对小窗口跨区间读写验证。

测试夹具使用独立照片 URI，避免打开照片时保存上一张编辑参数覆盖下一组夹具。矩阵输出逐组转存电脑并清理本轮生成文件，保留原片和应用资料。模拟器磁盘曾因未回收的大图测试文件不足，已只清理本轮输出并重跑；不把空间不足或测试夹具错误冒称产品渲染错误。

首轮总入口 207 条有 5 条 UI 失败：旧脚本仍点击已改名的“暗房”、旧导入入口和没有滚到的参数。更新为当前“放印”、菜单导入与可见性滚动后，剩一处系统照片选择器确认按钮文字在不可点击子节点上的识别错误；修正后独立 UI 12 条全部通过。脚本选择真实照片后检查新 URI、实际解码与渲染，未用注入回调冒充系统选择器交互。独立 UI 入口还增加新 Activity/task 和启动页等待，防止前一个测试状态影响本组。

完整观景台输出组实际复现取消结果丢失，修复后四条全部通过：布局规划、独立像素预期、源图/编辑变化及 pending 文件安全、真实 PNG/JPEG UI 导出和取消后继续编辑。其失败现场和最终结果分别保留。

## 最终功能与严格窗口结果

- 59 组功能入口通过，最新结果合并为 297 个不同用例；总入口单独为 207 条、0 失败。包含导入/异步切换、智能显影、材料/对比、裁剪/旋转/历史、曲线/HSL/混合器/色轮、预设/复制、照片管理/源恢复/编辑版本、观景台项目/拼图/吸附、单张/批量/快捷导出、缓存、发布恢复、进程死亡/设备丢失、元数据/日期/键盘及旧数据迁移。
- 10 种历史 RAW 的默认/自定义白平衡预览、相机元数据和导出采样与旧解码参考逐位一致；另通过 HE RAW 独立解码参考、处理中取消、截断文件拒绝、全尺寸 TIFF 和真实界面导入。
- 128 MiB 硬绑定、8 MiB 工作窗口：7 组 8193×281 全 RGBA16 对照；裁剪旋转/日期两组；十种片边 × 两种模式的 20 组完整像素对照通过。真实 NEF 的 6301×5819 正式 PNG 也在相同限制下通过。
- 同一严格策略下，一次性导出的 42 组材料/相纸/几何/颗粒/缓存负片消费对照及取消后重开通过。
- 14 项 Python 主测试、优化模式下的 3 项 SPIR-V 反例测试、47 个实际窗口模块 ABI、分包检查和 diff 空白检查通过。Debug、AndroidTest、Release 均构建成功。

严格扩展初轮发生过模拟器系统中断：`system_server` Watchdog 记录 ActivityManager/显示等线程阻塞 71 秒，随后系统界面、电话进程和应用出现 `DeadSystemException`。该轮没有完成结果，保留为失败；恢复后以新增逐用例日志重跑，完整通过。没有证据将其直接归因到某个照片内核，也不把恢复后的绿灯当作消除一切长时运行风险。证据为 `strict-system-full.log`、`strict-recovered.log` 和 `.tmp/libraw-upgrade/raw-film-strict-recovered/`。

最终 Kotlin 修复后的六份原生库和 193 项引擎资源，与 128 张矩阵运行时全部一致（合计 199 项）；因此观景台取消回调补丁不改变矩阵中已验证的渲染输入。相关总入口、观景台输出和导出/批量/host/编码/发布/保护等用例在最终构建重新运行。

## 原图导出耗时

同一 DSC_5099.NEF、CineStill 800T / Vision 2383、物理光晕、默认颗粒/眩光、原始尺寸、JPEG 95、不保留 EXIF。计时从应用提交导出到完成相册发布和预览会话恢复，不含电脑转存文件；缓存用例核对实际 hit 计数。修复前/后各三轮顺序测量，未做交错随机化，不能把小幅差异解释为设备无关的性能提升。

| 模式 | 修复前中位数 | 修复后中位数 | 修复后三轮范围 |
| --- | ---: | ---: | ---: |
| 无片边，首次/冷渲染 | 10.886 秒 | 10.822 秒 | 10.796–11.087 秒 |
| 无片边，已确认缓存命中 | 1.267 秒 | 1.307 秒 | 1.287–1.539 秒 |
| 135 整条片边，冷渲染 | 11.872 秒 | 11.092 秒 | 10.761–11.171 秒 |
| 135 扩展片门，冷渲染 | 9.705 秒 | 9.785 秒 | 9.711–12.906 秒 |

每种设置在所有重复和两种构建之间，完整 JPEG 文件 SHA-256 一致。片边输出按已有缓存策略不长期缓存，不能用无片边的 1.3 秒缓存数字描述片边原尺寸速度。范围显示存在波动；未测 ARM 手机温控或峰值总内存。证据：`performance/before.json`、`after.json`、`summary.json`。

含日期和后期调色的矩阵是另一组设置，不与上述重复样本混算。NEF 整条片边原尺寸单次样本：JPEG 12.168 秒、PNG 16.582 秒、sRGB TIFF 13.171 秒、P3 TIFF 13.386 秒。50MP DNG 带片边原尺寸单次样本：JPEG 21.646 秒、PNG 30.828 秒、sRGB TIFF 27.628 秒、P3 TIFF 40.587 秒。矩阵运行期间还在逐张转存验证，且每种只一个样本，因此它们仅是本轮测试观测，不是稳定的格式速度排名或手机指标。
