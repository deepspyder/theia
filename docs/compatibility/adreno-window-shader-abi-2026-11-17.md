# Adreno 830：公共窗口着色器接口排查

日期：2026-11-17。基线为原 v0.1.7、单内核 DIR 验证包，以及客户两轮实际失败信息。版本号保持 0.1.7、versionCode 8。本报告用于替代“只修复一个 DIR 内核即可解决所有导出”的判断。

## 确认了什么

客户的后续截图显示 `vkCreateComputePipelines` 创建 `spk_matmul3.windowed` 返回 `-13`，关闭优化后仍返回 `-13`。GPU、vendor、device、driver 与上次 DIR 失败一致：Adreno (TM) 830、20803、1141178369、2150760528。反馈固件为 `PD2454C_A_17.2.12.0.W10.V00 OL`，反馈系统 Android 17。

`spk_matmul3` 是通用三通道矩阵变换。它被相纸扫描后的 XYZ→输出 RGB 等路径使用，不是 JPEG 编码、日期绘制或 RAW 解码。图片先解码并进入处理，程序按需要延迟创建尚未使用的 GPU 管线，所以可以在进度 40%～60% 时才发现下一条编译失败。进度百分比不是精确的算法位置，更不等于该比例的照片已经被正确保存。

两条不同的窗口内核在同一驱动上失败，说明单独改 DIR 不足以覆盖兼容范围。由于本次照片和参数未必与上次相同，不能仅凭错误内核变化宣称 DIR 已在真机通过。

失败明确发生在这条管线被提交执行之前：不是该条矩阵运算产生了错误像素，也不是 JPEG 质量不够或文件编码错误。`VK_ERROR_UNKNOWN` 本身不能进一步证明显存不足、驱动内部哪条指令失败，或某句 GLSL 一定非法。

## 共用底层代码

`tools/windowed_shaders.py` 原来统一给 47 个非集体内核增加：

1. 推送常量 `base`、`end` 和 `uint origin[16]`。
2. 以 `base + gl_GlobalInvocationID.x` 保留绝对像素编号。
3. 把所有存储访问改成 `uint(original_index) - origin[binding]`，其中也包括从未移动的矩阵、计数、标志和查找表。

例如矩阵的原始 `matrix_data.value[0]` 被改写为 `matrix_data.value[uint(0) - theia_dispatch.origin[1]]`。运行时该参数表的 origin 确实是 0，但编译器仍必须处理推送常量数组、动态存储索引和无符号减法。原版预览使用没有这些新增访问的原始着色器，导出使用单独窗口变体，因此可能出现预览能用、导出不能创建管线。

这是实际存在的公共差异和兼容排查方向，不是厂商编译器根因的唯一证明。两个内核失败的共同点还不足以确定数组访问、固定表减法或另一项内部编译优化中的哪一项触发了错误。

同样不能仅凭 `-13` 排除驱动内部资源分配失败：管线创建也需要驱动资源，而旧截图没有当时的堆使用或厂商编译日志。新加入的不读取照片的管线预检，就是供同一真机进一步区分这两类情况：若空载也拒绝相同模块，更支持编译/接口形式问题；若空载全部成功而大图处理时才失败，还必须继续核对资源压力，不能只归罪于一条 GLSL 表达式。模拟器空载成功本身不能作此区分。

## 合法性验证与局限

- 旧矩阵 SPIR-V 已反汇编核对：只声明 `Shader` 能力；推送字段偏移为 0、4、8，origin 数组步长为 4，总范围为 72 字节，与 C++ `Push` 一致；没有发现本例需要额外启用的特殊能力。
- 旧版全部着色器已通过 `spirv-val`，本轮又通过实际 Vulkan 调度检查旧版。Khronos 官方 Android 验证层 `vulkan-sdk-1.4.363.1` 已由系统明确加载，旧版严格窗口像素回归未出现 `VUID` 或 Validation Error。
- 新版对 49 个已注册内核分别检查原始与导出模式，共 98 项预检通过；数学探针、拆分探针与集体 reduction 按原合同复用原始模块，对应 95 个不同的实际缓存管线。官方验证层下的新版预检和严格 8 MiB 窗口回归同样无 Validation Error。
- 验证设备为 API 37 x86_64、GFXStream、宿主 NVIDIA GPU。标准验证层可以检查 API 与 SPIR-V 合同，不能代替 Qualcomm 专有编译器执行，也不能保证覆盖所有厂商问题。

官方验证层只注入本地测试 APK；没有加入正式 APK。模拟器 GPU 调试设置在结束后恢复，诊断属性恢复为 0。证据保留在 `.tmp/adreno-window-core/vvl-test/` 和 `vvl-baseline-test/`，包含明确的 `Loaded layer VK_LAYER_KHRONOS_validation` 激活记录，不能把未加载验证层的空日志冒称验证通过。

## 公共适配措施

本次统一调整公共生成器，而非继续给矩阵内核添加单独替代：

- 将推送数组改成带显式 offset 的 18 个 uint 标量字段。仍是原有 72 字节布局，避免窗口地址需要通过数组访问链读取。
- 从 C++ 调度器的同一 `Rule` 表生成可移动绑定掩码。固定参数与查找表保留原始索引表达式，只有确实会移动的图片/工作区绑定才做偏移换算。
- 为 FIR、IIR、几何、采样和复制合同明确列出额外移动绑定。CPU 在提交前拒绝固定表起点非 0 的情况，防止日后两端合同悄悄漂移。
- 保留绝对随机编号、完整 IIR 递推、FIR 邻域和描述符范围限制。没有通过把所有内核局部化而重复颗粒或破坏空间算法。
- 新变体命名为 `.windowed-v3.spv`，报错带 `window_abi=scalar-origins-v3`，引擎缓存身份同步更新。构建前直接检查实际 SPIR-V 二进制：18 个 uint 标量、每字段偏移、72 字节布局、无动态推送数组访问和固定表约束。避免新原生库误配旧窗口文件。
- 新增 ADB 显式开启的全内核预检 `debug.theia.pipeline_preflight=1`。不读取照片，完成 98 项原始/导出模式管线预检并逐项记录，完成后销毁临时管线并恢复普通启动。默认不运行，不给正常启动或导出添加整套预编译成本。

前一包的原始 DIR 分批路径保留，其画质回归继续成立。其他窗口内核都使用新的公共接口。96 个原始和 bounded SPIR-V 二进制不变；47 个窗口变体只改变接口和地址表达式，浮点照片运算与材料光谱数据不改。

## 本轮验证合同

新增客户 JPEG 为 4080×3072、无 EXIF 旋转标志，使用附件原文件而非聊天缩略图。旧两张客户 JPEG 和真实 6064×4040 NEF 继续纳入。

测试使用同源码 Debug UI 与 Release 原生库宿主；最终交付为独立签名 Release，二者 DEX 不声称相同。原始完整调度作为画质参考，窗口路径必须与之完整 RGBA16 相同，不能只比较截图或文件头。正式导出通过 `:render`、缓存和相册保存，再由独立解码器核对完整 PNG RGB8、TIFF RGB16；JPEG 使用实际有损误差门槛。

### 完整成片验证

- 原生 25 组：三张客户 JPEG × 四种胶片 × 日期开关，加全尺寸 NEF × CineStill 800T/Vision 2383。全部完整 RGBA16 摘要相同，其中旧两张 JPEG 和 NEF 的 17 组同时与原发布包摘要一致。
- 实际文件共 99 张：每张 JPEG 的 Portra 400 日期开关各覆盖 2048、2560、3840、原尺寸，另有 CineStill 800T、Velvia 100、HP5 Plus 各开启日期并覆盖 2560；每个组合输出 JPEG、PNG、TIFF sRGB。不是所有胶片的全部尺寸排列，也没有新增 P3 全矩阵验收。
- 独立解码整个文件：33 张 PNG 的 RGB8、33 张 TIFF 的 RGB16 全通道差异为 0；33 张 JPEG 的最大单图平均绝对通道差为 2.732819/255。新客户原尺寸严格为 4080×3072，其余为 3072×4096、4096×3072；同尺寸参考和输出完全对应。
- 更严格的 8 MiB 工作窗口、128 MiB 存储绑定限制下：7 组 8193×281 场景覆盖多段和 DIR 强度边界/正片，2 组几何与片边日期对照通过；42 组材料、相纸、几何、颗粒和缓存负片消费对照通过。取消后重开及独立渲染进程的死亡重启、匿名描述符、身份拒绝、设备交接等回归通过。
- 47 个新窗口二进制的有序浮点运算类别与 GLSL 扩展运算代码序列保持；该检查只能补充地址修改范围的证据，不能替代上述整图像素比较。

证据：`native-verification.json`、`matrix/pixel-verification.json`、`floating-operation-verification.json`，以及 `.tmp/libraw-upgrade/window-core-strict/summary.json`。

### RAW 耗时和内存

关闭诊断属性后，以原版/新版/新版/原版/原版/新版交错，各三轮。在当前相同输入、模拟器和编码设置下，六轮原生 TIFF 与正式 CineStill 原尺寸 TIFF 文件摘要保持一致，GPU 池帧峰值均为 1,243,027,572 字节。

## 交付与剩余问题

验证包：`app/release/v0.1.7-window-v3/Theia-v0.1.7-window-v3-universal.apk`，58,426,606 字节，SHA-256 `5697dba39dab49ff0d3b111912a0bb8b808035482fd833f574af4f31cc486c92`。版本仍为 0.1.7/code 8，原证书 V1/V2/V3 验证通过，双 ABI 六个 SO 的 LOAD 和 APK ZIP 16 KiB 对齐通过，正式包不含官方验证层。

与原 v0.1.7 相比，146 个共同的引擎资源条目逐字节保持，47 个旧窗口变体被对应的 v3 替代；96 个原始/bounded 模块保持。DEX 因引擎身份与资源清理逻辑调整而重新构建，不能再声称 DEX 与旧包相同。预览、数据库和照片数据不参与清理。

仍需客户同固件验证新接口，不能把当前适配包叫作已经解决专有驱动内部故障。若新模块仍失败，须保留 `.windowed-v3`、`window_abi`、创建阶段及同一驱动信息，并在该设备做无照片预检和具体内核的最小差分，结合驱动日志区分编译与资源分配问题。ARM 真机耗时、温控、峰值内存与全格式验收继续保持待办。
